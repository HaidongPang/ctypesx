# Layout and portability

ctypesx uses the running CPython process's native ctypes ABI. It guarantees
consistency with the compiled ctypes layout it creates; it does not emulate a
different target compiler, architecture, operating system, or byte order.

## Host-native properties

The following come from the host:

- sizes and alignments of `short`, `int`, `long`, `long long`, pointer-sized
  integers, `size_t`, and `wchar_t`;
- structure and union padding;
- bit-field allocation and ordering;
- native endianness;
- pointer width and representation;
- floating-point and complex storage availability; and
- the platform calling convention used by ctypes.

Fixed-width `S8`/`U8` through `S64`/`U64` fix integer width, but the containing
record still uses host alignment and byte order.

## Unsupported layout controls

The current release supports only natural native layout. It rejects direct
ctypes declarations of:

- `_pack_`;
- `_align_`;
- `_layout_`; and
- `_anonymous_` field flattening.

There are not yet record class keywords for packed/custom layout or non-native
byte order. `ctypes.BigEndianStructure`, `LittleEndianStructure`, and equivalent
cross-endian record families are not modeled.

Rejecting these forms is deliberate: silently ignoring one would produce valid
Python code with the wrong ABI.

## Validate against the C toolchain

For every supported OS/architecture/compiler combination, compare ctypesx with
a small C layout probe built from the real header.

At minimum verify:

- `sizeof(record)`;
- `_Alignof(record)` or the compiler equivalent;
- `offsetof(record, field)` for ordinary fields;
- object bytes for representative values; and
- static header size and several instance extents for a FAM record.

Python-side example:

```python
import ctypes

from ctypesx import field_info


assert ctypes.sizeof(Packet) == c_sizeof_packet()
assert ctypes.alignment(Packet) == c_alignof_packet()
assert field_info(Packet, "ports").offset == c_offsetof_packet_ports()
```

Bit-fields cannot be passed to `offsetof`. Have the C helper initialize them,
copy the record bytes, and compare with an independently initialized ctypesx
record. Validate bit-fields per target and pass them to foreign functions by
pointer.

Comparing a migrated ctypes record with a ctypesx record is useful regression
coverage, but proves only that both Python declarations agree. It does not prove
that either matches the actual C header.

## Dynamic record size

For a record with a flexible tail:

- `ctypes.sizeof(RecordType)` is the static C `sizeof` prefix;
- `ctypes.sizeof(instance)` is the complete current ctypes allocation;
- `len(bytes(instance))` is the same complete extent with a copy; and
- `memoryview(instance).nbytes` is the complete extent without a byte copy and
  pins the allocation until release.

Do not use the class size as the byte count for a specific dynamic message.
Dynamic records must cross the C boundary by pointer.

The current FAM model requires the tail offset to equal the static class size.
Some compilers may place trailing padding such that these differ; ctypesx
rejects that layout instead of guessing whether padding belongs to the tail.

## Native bytes are not serialization

`bytes(record)` includes native:

- padding, potentially with zero-initialized but semantically irrelevant bytes;
- endianness;
- pointer values;
- bit-field representation; and
- ABI-specific widths.

Use it only for a kernel/device/library interface that explicitly consumes the
same ABI object representation. For files, networks, or long-term storage, use
an explicit serialization format with declared endianness and widths.

## `long double` and complex caveats

`CLongDouble` has the native `ctypes.c_longdouble` layout, but Python and ctypes
surface its value as Python `float`; precision beyond binary64 is not preserved
in the semantic value.

C complex ctypes were added as optional Python 3.14 facilities. Availability
depends on the Python/libffi build. ctypesx complex classes are importable for
feature detection and raise `NotImplementedError` when directly constructed
without matching native storage. A record declaration using an unavailable
complex type fails at class creation with `TypeError`.

## Cross-target and generated bindings

ctypesx does not calculate the layout of a guest or remote target. Running an
x86_64 Python process cannot use it to emulate an arm64 C ABI by changing a
flag. Build and validate bindings on the actual target, or use a separate
cross-target serialization/layout tool.

The package also does not parse headers. Constants, records, and enums must be
declared by the binding author or generated by an external tool before import.
